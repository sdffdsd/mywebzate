# 留言板：公开留言 + 私信推送

> 状态：**代码已完成，未部署**。本文记录探索过的路径、最终选型、实测结果，
> 以及上线前还需要做的决定与操作。

## 一、要做的事

| 通道 | 谁看得到 | 推送 |
| --- | --- | --- |
| 公开留言 | 所有人，留在 `/guestbook/` 页面上 | 无 |
| 私信站主 | 只有你（管理口令可见） | 落库的同时推到你手机/微信/机器人 |

两条通道共用一套校验与身份识别，只在 `visibility` 上分叉 —— 这样不会出现
「公开的那条被拦了、私信那条漏过去」这类不一致。

唯一的例外是**冷却窗口**，它按通道各算各的（见第五节）。两边共用会得出反的效果：
「刚发过一条公开留言」会把私信一起锁住，而该收紧的恰恰是私信。

## 二、昵称从哪来：候选路径与取舍

目标是「不用注册也有个稳定的名字，能区分不同的人」。逐条看：

| 方案 | 稳定性 | 区分度 | 问题 | 结论 |
| --- | --- | --- | --- | --- |
| 纯 IP | 换网络就换人 | 差：同一出口（学校/公司/家庭 NAT）所有人一个名字 | 也挡不住 VPN 轮换 | ✗ |
| IP + UA 大类 | 同一台设备长期不变 | 好：同 IP 的不同手机/电脑能分开 | 换浏览器算另一个人 | **采用** |
| Cookie / localStorage | 最稳 | 最好 | 清缓存即丢，且可随意伪造 | 作为兜底思路保留 |
| 浏览器指纹（canvas/WebGL） | 好 | 好 | 不稳定（升级就变）、涉隐私、易误伤 | ✗ |
| 访客自填署名 | — | — | 没人愿意填 | 保留为「可选覆盖」 |
| 地理位置（country/city） | — | 有辨识度但**不该公开** | 等于公开访客位置 | 只给管理视角 |

最终做法：

```
visitorId = SHA-256(salt | device | IP | 系统-浏览器大类).slice(0, 10)
rateKey   = SHA-256(salt | rate   | IP).slice(0, 10)
昵称       = 形容词[hash 前 2 位] + 名词[hash 3-4 位] + " #" + hash 5-8 位
```

- 例：`深礁石 #7ab7`、`青光缆 #2419`。形容词 24 × 名词 24 = 576 个组合，
  重名再靠 `#后缀` 区分。
- **原始 IP 不落库、不回传**，只留 10 位十六进制指纹；指纹的盐由你持有，
  换盐 = 给所有访客重新分配身份。
- 身份分两层：昵称用「设备级」指纹（同 IP 不同设备能分开），限流用「出口级」指纹
  （换 UA 也躲不掉）。实测：同 IP 同 UA 两次 `whoami` 得到同一个昵称；
  同 IP 换 iPhone Safari 得到另一个昵称。
- 边界要讲清楚：**换浏览器、换网络、开隐私模式都会变成「另一个人」**；
  同一台设备长期不变。这是「不登录」的代价，也是它不追踪人的原因。

## 三、存储路径

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| **KV（采用）** | 已有绑定、零新增基建、读多写少足够快 | 无事务、`list` 只能按前缀 + 键名排序 | ✓ |
| D1 (SQLite) | 分页、检索、审核状态、删除都更顺手 | 要新建库 + migrations，量级用不上 | 未来若要做审核队列再换 |
| Durable Objects | 实时聊天室级别 | 对留言板过重 | ✗ |
| 外部 BaaS | 有现成后台 | 多一个第三方与合规面 | ✗ |

KV 键布局（`key` 前缀刻意分开，公开列表不必读私信的值）：

| 键 | 值 | 用途 |
| --- | --- | --- |
| `gbp:<取反时间戳>:<id>` | 留言 JSON | 公开留言，键名升序 = 时间倒序 |
| `gbx:<取反时间戳>:<id>` | 留言 JSON | 私信 |
| `gbidx:<id>` | 上面那个键名 | 删除时 O(1) 反查，不用全表扫 |
| `gbcount:public` / `gbcount:private` | 数字 | 列表页显示条数 |
| `gbrl:<rateKey>` | 上次提交时间 | 公开留言的冷却（20 秒） |
| `gbrl:<rateKey>:dm` | 上次提交时间 | 私信的冷却（默认 5 分钟），与公开那条互不牵连 |

冷却记录的 TTL 取 `max(60, 窗口)`。KV 的 `expirationTtl` 下限是 60 秒，而私信窗口是
300 秒 —— 若把 TTL 照旧写死 60 秒，私信冷却会在 60 秒后随键过期**静默失效**，
而且表面上完全看不出来。判定始终以值里的时间戳为准，TTL 只负责事后回收。

## 四、私信怎么推给你

三条通道可以同时配，谁成功算谁，接口用 `channels` 字段如实回报（例如
`["resend","webhook"]`）。**任何一条通道失败都不影响留言落库** ——
读者不该为站主的通知配置背锅。

### 4.1 邮件（推荐，你要的就是这个）

| 方式 | 要配什么 | 说明 |
| --- | --- | --- |
| **Resend**（推荐） | `RESEND_API_KEY` + `GUESTBOOK_EMAIL` | 免费 3000 封/月、100 封/天；纯 HTTP API，不用自建 SMTP。**先不改 DNS 也能用**：发件人留空即走 `onboarding@resend.dev`，只能发到你自己注册 Resend 的那个邮箱 —— 正好是这里的用法。想让发件人显示成 `noreply@za4ever.com`，就在 Cloudflare DNS 里加它给的三条记录（SPF/DKIM），两分钟的事。 |
| Cloudflare Email Routing | `GUESTBOOK_MAILER` 绑定 | 零第三方、免费，但要先在你的域名上开 Email Routing 并把收件地址加进「已验证目的地」，再把 `send_email` 绑定到 `GUESTBOOK_MAILER`。Pages Functions 对 `send_email` 的支持还不确定，跑在 Worker 上最稳 —— 所以这条留作备选。 |
| 其它邮件 API | 想用 SendGrid / Postmark 等 | 它们的 HTTP API 都是同一个形状，照着 `notifyResend()` 加十行即可。 |

邮件正文长这样，一眼能判断要不要回：

```text
<留言原文>

————————————
来自：深礁石 #7ab7
时间：2026-09-27T09:52:42.408Z
地区：CN
设备：ios-safari
编号：3d262424d6c256b4
```

### 4.2 手机推送（可选，比邮件更快）

`GUESTBOOK_PUSH` 一个地址，报文形态自动适配：

| 通道 | 填什么 | 报文 |
| --- | --- | --- |
| Bark | `https://api.day.app/<你的key>` | JSON `{title, body}` |
| Server酱 | `https://sctapi.ftqq.com/<key>.send` | 表单 `title` / `desp` |
| 其它（ntfy / 企业微信 / 飞书 / 自建） | 你的 webhook | JSON `{title, body, nickname, createdAt, country}` |

**Bark 是什么**：一个免费开源的 iOS 通知 App，装上以后它给你一串专属网址
（形如 `https://api.day.app/xxxxxxxx`），往这个网址 POST 一句话，你的 iPhone
就弹一条通知。不用注册、不用付费，适合「只给自己推送」的场景；
它是 iOS 独占的，安卓对应的是 ntfy 这类。邮件和 Bark 不冲突，
想两边都收就两个都配。

### 4.3 什么都不配

私信照样落库（`pushed:false`），你带管理口令访问
`/api/guestbook?scope=all&key=...` 就能读到。

## 五、反滥用

已实现：蜜罐字段（故意回 202 让脚本以为成功）、填表耗时 < 1.5 秒判为脚本、
正文 ≤ 400 字、署名 ≤ 24 字、链接超过 2 条拒收、请求体 ≤ 8 KB、
控制字符与多余空白归一化、前端一律 `textContent` 渲染（无 XSS 面）。

### 5.1 冷却：同一个用户，两条通道分别计时

身份用「出口级」指纹（IP，换 UA 躲不掉），窗口按通道分开：

| 通道 | 窗口 | 冷却键 | 怎么调 |
| --- | --- | --- | --- |
| 公开留言 | 20 秒 | `gbrl:<rateKey>` | 核心默认 `PUBLIC_COOLDOWN_SEC` |
| 私信站主 | **5 分钟**（300 秒） | `gbrl:<rateKey>:dm` | `GUESTBOOK_DM_COOLDOWN`（秒），设 `0` 关闭 |

两件事必须分开算，否则会互相误伤：公开留言发得松、私信收得紧，共用一把锁的话
「刚发过一条公开留言」就会把私信一并锁 5 分钟。

被拦时回 `429 {error:"rate_limited", retryAfter:<还需秒数>, cooldownSec, visibility}`。
带 `retryAfter` 而不是干巴巴的 `rate_limited`，是为了让前端能倒计时；
发成功时（201）也回 `cooldownSec`，前端可以立刻把按钮锁上，省得白点一次。
**服务端始终是权威**，前端那层纯粹是体验。

两个已知边界，写在这里免得以后当成 bug：

- 判定用出口 IP，所以同一 NAT（家里、公司、学校）下的两个人共用一个冷却。
  换成「设备级」指纹并不会更严 —— `visitorId` 本身就由 `salt|device|IP|platform`
  算出，含 IP，拿它做冷却只会更松。
- KV 没有原子操作，`claim` 是「读—比—写」，同一出口**同时**发出的两条理论上
  可能都过。原有的 20 秒限流也是这个性质；要严格串行得上 Durable Objects，
  对留言板不值当（见第三节的取舍表）。

还可以加（本次没做，等你决定）：

- **Cloudflare Turnstile**：免费、无感，服务端 `siteverify` 校验；对抗脚本最有效。
- **先审后发**：留言带 `status: pending`，管理口令通过后才出现在列表里。
  目前是**自动公开**，适合小站；要做审核队列建议顺手迁到 D1。

## 六、管理

```bash
# 读全部（含私信，带指纹/地区/平台）
curl -s "https://za4ever.com/api/guestbook?scope=all&key=<GUESTBOOK_ADMIN>"

# 删一条
curl -s -X DELETE "https://za4ever.com/api/guestbook?id=<id>&key=<GUESTBOOK_ADMIN>"
```

没配 `GUESTBOOK_ADMIN` 时管理接口一律 403 —— 默认是关的。

## 七、本次本地实测（未部署）

两条运行时链路都真跑过：

1. **Node 备用出口**（`node server/index.mjs`）：公开留言 201、私信 201 且不出现在公开列表、
   管理视角带口令能读到私信与指纹、无口令 403、连发第二条 429、
   蜜罐与秒填秒交 202 且不落库、链接过多 400、删除后条数归零。
2. **Cloudflare 侧**（`npx wrangler pages dev dist --kv GUESTBOOK`）：
   同样的写入 / 公开列表过滤 / 管理视角 / 限流全部通过，KV 键布局与计数正常。
3. **冷却**（可控时钟快进 + 一个如实执行 `expirationTtl` 的假 KV，直接加载
   `functions/api/guestbook.ts` 走 `onRequest`）：私信 t+0 放行（`cooldownSec:300`）、
   t+1 拦（`retryAfter:299`）、t+61 仍拦、t+299 拦（`retryAfter:1`）、t+301 放行；
   同一 IP 的公开留言不受私信冷却波及（`cooldownSec:20`，公开留言自己 20 秒一条）；
   被拒的提交（400）不消耗冷却；`GUESTBOOK_DM_COOLDOWN=0` 时连发两条都放行。
   Node 出口另用 curl 复核，行为一致。

   TTL 那一条还做了**对照实验**：把 TTL 改回写死的 60 秒，t+61 发出的第二条私信
   会返回 `201` —— 静默放过。所以 `max(60, 窗口)` 不是防御性冗余，是必需的；
   这类 bug 不看时钟快进根本测不出来。

   三条存储实现都实测过：KV（上面这个假 KV）、Node 文件存储（curl 打 Node 出口）、
   以及没绑 KV 时的内存兜底。最后这条顺带暴露了一个**先前就存在**的 bug：
   `createMemoryStore()` 原本在 `onRequest` 里现调，每个请求都新建空 Map ——
   留言存不住、冷却也永不触发（实测第二条私信照样 201）。已改成模块级单例：
   Workers 的模块状态在同一 isolate 内跨请求存活，兜底才有意义。

副作用记录：workerd 本地会给请求带上 `cf-connecting-ip`（值为本机），
所以本地测试时 `x-forwarded-for` 不起作用 —— 真实环境里这个头由 Cloudflare 写入、
客户端伪造会被覆盖，正好是我们想要的。


   `GUESTBOOK_SALT` 不配会用开发默认值 —— 上线前必须配，且别换（换盐 = 全员换名）。
3. 部署后按第六节用 curl 各验一遍；确认私信真能推到你手机上。

## 九、已定的与待定的

1. 公开留言**直接上墙**（不做先审后发）。
2. 入口**只留顶部导航**里的「留言」，首页不动。
